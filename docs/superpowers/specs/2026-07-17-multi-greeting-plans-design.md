# 主动招呼多计划与登录判定设计

## 目标

- 将单个主动招呼设置改为可新建、编辑、启停、删除和单次执行的计划列表。
- 阻止多个已启用计划的时间范围重叠，并返回可理解的冲突信息。
- 保留现有计划配置和执行记录。
- 修复 BOSS 页面切换期间把已登录账号误判为未登录的问题。

## 数据模型

新增 `greeting_plans` 表：

- `id`：计划标识。
- `name`：计划名称。
- `enabled`：是否启用。
- `daily_limit`、`hourly_limit`：账号级每日和每小时阈值。
- `start_at`、`end_at`：精确到分钟的执行时间范围，按 `[start_at, end_at)` 计算。
- `paused_reason`、`created_at`、`updated_at`：暂停原因和审计时间。

`greeting_logs` 增加可空的 `plan_id`。已有单计划首次迁移为“默认招呼计划”；旧日志保留，未能关联计划的记录仍可查看。旧表保留但不再写入，避免破坏用户数据的迁移操作。

## 冲突与调度

- 停用计划允许任意保存。
- 新建、编辑或启用计划时，只要它与其他已启用计划满足 `start < other.end && end > other.start`，请求就以 `409` 拒绝，并返回冲突计划名称与时间。
- 首尾相接不算冲突。
- 调度器仍只有一个后台线程和一个执行锁。它从已启用计划中选择当前到期计划，因此不会并发点击 BOSS。
- 每日计数、每小时计数和上次发送时间按 BOSS 账号全局统计，避免多个计划叠加突破账号频率。
- 发送成功或失败均记录所属计划。安全验证、明确登录失效、额度用尽或结果未知时，仅暂停正在执行的计划。
- 每次执行结束后继续尝试返回沟通页。

## 接口

- `GET /api/greeting-plans`：返回计划及实时状态。
- `POST /api/greeting-plans`：新建计划。
- `PATCH /api/greeting-plans/{id}`：编辑或启停计划。
- `DELETE /api/greeting-plans/{id}`：删除计划。
- `POST /api/greeting-plans/{id}/run-once`：执行该计划当前到期的一次任务。
- `GET /api/greetings/logs`：保留执行记录接口，并返回计划名称。

删除正在执行的计划会被拒绝。空列表是合法状态，新计划默认从当前分钟开始、一天后结束。

## 界面

主动招呼抽屉改为计划列表：

- 顶部保留账号级今日、本小时和最近一次执行摘要。
- 每行显示名称、时间范围、频率、状态，以及启停、编辑、执行一次、删除操作。
- “新建计划”和“编辑”共用一个原生表单，日期时间继续使用 `datetime-local`。
- 冲突错误直接显示冲突计划和时间，不静默覆盖。
- 打开主动招呼仍将 BOSS 切到推荐牛人；关闭或执行完成后返回沟通页。

## 登录判定

根因是 BOSS 的单页应用在跳转后先创建 `<body>`，稍后才渲染登录标记。现有一次性文本检查会在中间状态返回未登录。

修复方式：

- 页面切换后轮询等待明确状态，最长等待数秒。
- 出现聊天联系人、推荐卡片或退出登录标记时判定已登录。
- 只有 URL 或页面明确进入登录入口时才判定未登录。
- 超时但未出现明确未登录证据时返回“页面尚未加载完成”，不把计划暂停为登录失效。

## 验收

- 单计划数据可自动迁移且内容不丢失。
- 可完成计划 CRUD、启停和单次执行。
- 启用计划重叠返回 `409`；相邻计划可启用。
- 多计划仍串行且使用全局频率计数。
- 从沟通页首次切到推荐页不会误报未登录。
- 现有聊天、AI 草稿、知识库和桌面启动流程不回归。
